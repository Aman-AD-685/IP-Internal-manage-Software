Industry Prime — IP Internal Management Software

Internal operations web application for Industry Prime teams: support tickets with multi-stage SLA, client onboarding, invoice & payment tracking, payment ageing, training pipelines, lead management, daily task checklists, and per-person KPI dashboards — all behind role- and section-based access control.

Production React 18 + TypeScript + Vite Ant Design FastAPI (Python 3.11) Supabase / PostgreSQL Vercel + Render

1. Overview

Industry Prime — IP Internal Management Software (also known as industryprime, previously an FMS-style system) is the internal management platform used by Industry Prime's operations, support, success, onboarding, and sales teams. It is a single web application with one shared login, where each user sees only the sections granted to them.

Skeleton loading states

Medium priority UI/Design. Full rollout spec: docs/UI_LOADING_AND_EMPTY_STATES.md. Staff wording: USER_GUIDE.html#loading-states.

Problem: Generic centered Spin / blank screens cause layout shift when data arrives, so the UI feels slower than measured load time.

Goal: Layout-matched Ant Design Skeleton placeholders (cards, table rows, chart blocks) so perceived load feels ~30–40% faster with the same network time. Prefer skeletons.tsx exports over new ad-hoc spinners.

6. Roles & Permissions

Access control has two layers, enforced both in the frontend (ProtectedRoute, sidebar filtering) and the backend (section_permissions_util.py, per-endpoint checks):

  1. Role — user approver admin master_admin stored via user_profiles.role_id → roles.
  2. Section permissions — per-user can_view / can_edit flags in user_section_permissions, keyed by section.

Section keys (kept in sync between PERMISSION_SECTION_KEYS in constants.ts and SECTION_KEYS in main.py):

dashboard · dashboard_kpi · improvement · improvement_i1 · soft_sugg · soft_sugg_details · support_dashboard · all_tickets · chores_bugs · staging · feature · approval_status · completed_chores_bugs · rejected_tickets · completed_feature · solution · task · success_performance · success_comp_perform · client_to_lead · leads · onboarding · onboarding_payment_status · client_payment · training · db_client · settings · users
  • master_admin automatically receives all dashboard permissions from the backend.
  • admin gets management and global-filter capabilities plus whatever section flags are assigned in the matrix.
  • Normal users see only their own scoped data and explicitly granted sections.
Project convention: grant dashboard sections through user_section_permissions (can_view=true), never by adding if email === … rules. Only two legacy pages (Pending Payment Details, DB-Dash) still use email allowlists.

7.6 Leads pipeline

Leads are created manually (POST /leads) or imported from TSV/sheets (/client-to-lead/import). Each lead carries per-stage JSON in lead_stage_data (e.g. lead_details, contacted, …) updated via PUT /leads/{id}/stages/{stage_slug}. Closed leads are listed separately.

7.7 KPI dashboards

  1. The universal dashboard first calls GET /dashboard/bootstrap for a fast initial paint, then loads details lazily.
  2. Per-person KPI: GET /dashboard/kpi?person=&month=&week= — the backend enforces who may view whose board (require_dashboard_kpi_person).
  3. Daily scores are entered into kpi_daily_work_log; specialized boards exist for Soumya (SLA snapshots), Souvik (EA tracker), and Adrija (social KPI).
  4. Backend caches are invalidated whenever tickets, checklist, or delegation data change, so KPI numbers stay current.

10. Cron Jobs & Email

There is no in-app scheduler. All recurring work is triggered by cron-job.org calling secured endpoints (setup guide: database/CRON_JOB_ORG_SETUP.md). The batch runner /cron/run-all-emails executes these job keys from cron_email_batch.py:

Job keyWhat it sendsStandalone endpoint / secret
feature_approvalFeature-approval reminder emails to configured recipients/feature-approval-reminders/run · FEATURE_APPROVAL_CRON_SECRET
checklist_dailyDaily checklist reminders per user/checklist/send-daily-reminders · CHECKLIST_CRON_SECRET
delegation_dailyDaily delegation reminders/delegation/send-daily-reminders · DELEGATION_CRON_SECRET
pending_digestPending-work digest email/reminders/send-pending-digest
escalation_pending / escalation_critical / escalation_stagesEscalation emails for pending, critical, and stage-delayed tickets/escalation/send-*-mails · ESCALATION_CRON_SECRET

Additional scheduled endpoints outside the batch: /cron/attendance-sync (mirrors attendance from a second Supabase project into attendance_sync_records) and /cron/soumya-sla-scan (weekly SLA snapshots). Deduplication tables (*_reminder_sent) prevent duplicate mails. A working-day check (/cron/working-day) skips holidays.

Email delivery: SendGrid HTTP API is preferred on Render (SMTP ports can be blocked); the system falls back to SMTP (Postmark / Brevo / Gmail) per EMAIL_PROVIDER / EMAIL_SMTP_FALLBACK settings in backend/app/utils/email.py.

Keepalive: .github/workflows/render-keepalive.yml pings /health every 5 minutes so the free Render instance stays warm.

11. Run & Deployment

Local development

# Backend (FastAPI on port 8020)
cd backend
python -m venv venv
venv\Scripts\activate          # Windows
pip install -r requirements.txt
# copy backend/.env.example → backend/.env and fill Supabase keys + secrets
uvicorn app.main:app --reload --host 127.0.0.1 --port 8020

# Frontend (Vite dev server on port 3001, /api proxied to the backend)
cd fms-frontend
npm install
# copy fms-frontend/.env.example → .env ; set VITE_API_BASE_URL=http://127.0.0.1:8020
npm run dev

Convenience scripts: start-all.ps1 / start-all.bat at the repo root, backend/start-backend.ps1.
