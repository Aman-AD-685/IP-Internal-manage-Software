# Daily journal — 2026-09-08

## Summary (1–3 sentences)

radhika@industryprime.com signed up in production and never got a confirmation mail, but the
user row was sitting in Supabase Auth with zero auth logs. Root cause: `_do_register` creates
the auth user *before* the Postmark send, and nothing rolled it back when the send failed —
so every retry then hit `generate_link signup → "already registered"` and the account was
permanently unreachable.

## Work completed

  (`REGISTER ROLLBACK <uid>: ... <get_last_email_error()>`). Removed the "registration
  successful but no email" message — `confirmation_sent` can no longer be a lie.
- `backend/app/password_reset_email.py`: `delete_auth_user()` — admin delete guarded by
  `get_user_by_id` so a **confirmed** account can never be rolled back.
- `SignupEmailTaken` message now points at Resend instead of only "please log in".
- `backend/scripts/check_signup_confirmation_email.py`: asserts rollback runs before
  REGISTER SUCCESS and that `delete_auth_user` checks `email_confirmed_at`.
- Gave the user the Supabase SQL to remove the stuck radhika row (profile then `auth.users`).

## Decisions & preferences

- Failing to send the confirmation mail must fail the whole registration — an orphan
  unconfirmed auth user is worse than making the user retry.

## Lessons for future reviews

- Any flow that creates an auth user then sends mail needs a rollback on send failure —
  GoTrue makes the second attempt un-retryable ("already registered").
- Never return a success payload whose flag says the side effect failed; the frontend
  ignores the flag and shows "check your email".
- Admin `delete_user` at a rollback boundary must verify the account is unconfirmed first.
